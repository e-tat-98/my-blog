## はじめに

大規模な電子書籍サービスの Web アプリケーションで、Nuxt 3 へのメジャーバージョンアップを推進しました。

移行の範囲は、Vuex から Pinia、Webpack から Vite、Express.js から Nitro への切り替えを伴う基盤刷新です。通常の機能開発と並行しながら、移行後の安定稼働まで持っていくことが仕事でした。この記事では、そのときにやったことと、振り返って効いたと感じていることを書きます✏

## 1. ドキュメントにない挙動は、ソースコードまで確認した

公式ドキュメントだけでは判断が難しい挙動がありました。とくに Options API の挙動です。ここでは推測で進めず、Nuxt のソースコードまで確認して調査・検証しました🔍

対象になったのは、データ取得の asyncData オプションです。Nuxt 3 では [defineNuxtComponent](https://nuxt.com/docs/3.x/api/utils/define-nuxt-component) というヘルパーを使えば Nuxt 2 の書き方を引き続き使えるとされていましたが、実際に移行してみると挙動が同じには見えません。とくに「いつ実行されるのか」という実行タイミングがドキュメントからは読み取れず、前提がずれるとデータ取得まわりの設計が崩れてしまいます。

調査の発端は、移行の初期にハイドレーションエラーが多発したことでした。Nuxt 3 では SSR と CSR でデータ取得が二重に走ってしまう問題があり、ドキュメント上は、[useAsyncData](https://nuxt.com/docs/3.x/api/composables/use-async-data) を使えばデフォルトで二重取得が回避できる（サーバーで取得した結果が payload でクライアントに引き継がれる）とされていました。とはいえ僕らは asyncData オプションをそのまま移行していたので、「この仕組みが asyncData でも効いているのか？」が分かりませんでした。

あわせて、middleware で Pinia の store にセットした値を、asyncData の中で「確定した値」として参照できるのか、という点も確認が必要でした。Nuxt 2 では middleware → asyncData という実行順が保証されていたので、この前提で処理を書けました。ところが Nuxt 3 では、asyncData がどのタイミングで、どの仕組みで実行されるのかがドキュメントからは読み取れず、同じ前提が成り立つのか判断できませんでした🤔

```vue
<!-- Nuxt 2：Options API の asyncData -->
<script>
export default {
  async asyncData() {
    const hello = await $fetch('/api/hello')
    return { hello }
  }
}
</script>
```

```vue
<!-- Nuxt 3：defineNuxtComponent でラップすれば引き続き使える、とされていた -->
<script>
export default defineNuxtComponent({
  async asyncData() {
    const hello = await $fetch('/api/hello')
    return { hello }
  }
})
</script>
```

ソースコードまで掘って確認したところ、defineNuxtComponent の内部では setup の中で useAsyncData が呼び出され、asyncData で定義した関数がその実行関数としてそのまま渡されていました。見た目は Nuxt 2 の書き方でも、実体は Nuxt 3 のデータ取得の仕組みの上で動いている、ということです。この前提が押さえられてからは、挙動を Nuxt 3 側の仕組みから説明できるようになり、移行前に不具合の芽を把握して対処できました。

実際のソースコードはこうなっています（抜粋・一部省略）。

```ts
// packages/nuxt/src/app/composables/component.ts
export const defineNuxtComponent = function defineNuxtComponent (...args) {
  const [options] = args
  const { setup } = options
  // ...
  return {
    ...options,
    setup (props, ctx) {
      // ...
      const promises = []
      if (options.asyncData) {
        promises.push(runLegacyAsyncData(res, options.asyncData))
      }
      // ...
    }
  }
}

async function runLegacyAsyncData (res, fn) {
  // ...
  const { data, error } = await useAsyncData(
    `options:asyncdata:${key}`,
    () => fn(nuxtApp)
  )
  // ...
}
```

参照：[nuxt/nuxt — packages/nuxt/src/app/composables/component.ts](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/app/composables/component.ts)

この仕組みと順序は、SSR でも CSR でも同じです。初回表示（SSR）ではサーバー側で middleware → setup（asyncData）が実行され、結果は payload としてクライアントに渡るため、クライアント側で再実行はされません。画面遷移（CSR）では、クライアント側で同じ順序で実行されます。違うのは実行される場所だけです。

ただ、この引き継ぎが効くのは、サーバーとクライアントでキーが一致したときだけです。キーを自動生成に任せきりだと、同じコンポーネントを並べたときにキーが衝突したり、条件によってはサーバーとクライアントでキーがズレたりして、引き継ぎが効かず、ハイドレーションエラーの一因になっていました。途中からは、クエリを含めたキーを明示的に渡す運用に変えて、この問題を回避しました。

キーの自動生成は、ソースではこうなっています（抜粋・一部省略）。

```ts
// packages/nuxt/src/app/composables/component.ts
function getFetchKey () {
  const vm = getCurrentInstance()!
  const route = useRoute()
  const { _fetchKeyBase } = vm.proxy!.$options
  return hashKey([
    _fetchKeyBase,
    route.path,
    route.query,
    route.matched.findIndex(r => Object.values(r.components || {}).includes(vm.type)),
  ])
}

async function runLegacyAsyncData (res, fn) {
  const nuxtApp = useNuxtApp()
  const { fetchKey } = getCurrentInstance()!.proxy!.$options
  const key = (typeof fetchKey === 'function' ? fetchKey(() => '') : fetchKey) || getFetchKey()
  const { data, error } = await useAsyncData(`options:asyncdata:${key}`, () => import.meta.server ? nuxtApp.runWithContext(() => fn(nuxtApp)) : fn(nuxtApp))
  // ...
}
```

`fetchKey` が設定されていればそれを使い、なければ `getFetchKey()` で自動生成する、という分岐です。

僕らの対応は、この `fetchKey` を使う形でした。クエリを含めたキーを明示的に返すようにしています。

```vue
<!-- クエリを含めたキーを明示的に渡す -->
<script>
export default defineNuxtComponent({
  fetchKey: () => {
    const route = useRoute()
    return `search-result:${JSON.stringify(route.query)}`
  },
  async asyncData() {
    const result = await $fetch('/api/search')
    return { result }
  }
})
</script>
```

## 2. 一番つまずいたのは「Nuxt instance is unavailable」だった

移行作業の中で一番つまずいたのは、`Nuxt instance is unavailable` というエラーでした。Nuxt の composable を呼んだときに発生するエラーで、出る場所やタイミングが一様ではなく、原因の切り分けに苦労しました🥲

Vue はライフサイクルの中で「現在のインスタンス」をグローバルな変数で一時的に保持し、同じ tick のうちに解除します。Nuxt も同様に nuxtApp を一時的に保持していて、composable はそれを頼りに動作します。

なぜこんな作りなのかというと、そもそもは Composition API の都合です。composable はただの関数なので、呼ばれたときに「今どのコンポーネントの setup の中か」を知る手段が要ります。そのために、setup の実行中だけ現在のインスタンスをグローバルに置いておく、という設計になっています。

さらに SSR では、話がもう一段シビアになります。サーバーでは複数のリクエストが1つのプロセスで並行処理されます。ここでいう「グローバルな変数」は、そのプロセスに1つだけ存在する共有変数で、全てのリクエストから参照・上書きできます。そのため「現在のインスタンス」を共有し続けると、別のユーザーの状態が混ざってしまいます（Cross-Request State Pollution）。それを防ぐため、インスタンスの保持は意図的に狭い範囲に限定されている。つまりこのエラーはバグというより、安全のための制約が表面に出たものだ、というのが僕の理解です。1章のソースでも、サーバー側の実行では [runWithContext](https://nuxt.com/docs/3.x/api/composables/use-nuxt-app) で文脈を明示的に引き継いでいました。

こういう「グローバルな変数で一時的に保持する」設計が成り立つのは、JavaScript がシングルスレッドだからです。同期的に実行されるコードは途中で割り込まれないので、保持している間に他の処理と混ざることがありません。

逆に、await を挟むとその前提が崩れます。だから、想定された場所以外で、あるいは await を挟んだ後で composable を呼ぶと、インスタンスが見つからずにこのエラーになります。

対処として、nuxt.config で [asyncContext](https://nuxt.com/docs/3.x/guide/going-further/experimental-features) を有効化しました。Node.js の AsyncLocalStorage を使い、処理中の Nuxt インスタンスを非同期処理の文脈に紐づけて保持する仕組みです。共有変数が「プロセスに1つの置き場所」だとすると、AsyncLocalStorage は「リクエストごとに別の置き場所」を用意するようなもので、await を挟んでも自分のリクエストのインスタンスが返ってきます。

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  experimental: {
    asyncContext: true
  }
})
```

正直なところ、発生条件を100%理解できたとは思っていません。ただ、根っこにあるのが「Vue のインスタンス管理の仕組み」と「SSR で状態混入を防ぐ制約」で、asyncContext がその橋渡しをするものだ、という整理まではたどり着きました笑

分からないなりに、制約の「理由」まで掘っておくと、対処の選び方が変わります。これはこの件で得た実感です。

- [Nuxt 公式ドキュメント — Experimental Features（asyncContext）](https://nuxt.com/docs/3.x/guide/going-further/experimental-features)

## 3. 機能開発と移行を並走させるために、移行用の場を分けた

移行期間中も、通常の機能開発は止まりません。並行すると必ず起きるのが、コードの競合と、機能差分・デグレードのリスクです。

そこで、移行用リポジトリと開発環境を整備し、最新コードの取り込みルールを定めました。ルールはシンプルで、取り込み済みのファイルの冒頭に、取り込んだ時点のリリースタグをコメントで残す、というものです。

```ts
// [Nuxt3] Release 2025.12.18
```

当時は月〜木にほぼ毎日リリースがあり、バージョンは日付のカレンダータグで管理されていました。このコメントで、そのファイルが「いつ時点の本流まで取り込み済みか」が一目で分かります👀

あわせて git の diff で現行バージョンとの差分を出力できるようにし、最終的に差分が残っていないかを機械的に確かめられるようにしました。

進捗・タスク管理と移行手順の整備も担当でした。移行の実装そのものと、チームが迷わず進めるための段取りは、同じ仕事として扱いました。

## 4. 調査結果は GitHub Discussions に残し、追加メンバーが自力で追えるようにした

移行の途中でメンバーが追加で参画しました。追加メンバーのキャッチアップを支えるため、調査結果や実装上の注意点を GitHub Discussions で共有し、個別の技術支援も行いました。

狙いは、聞かないと分からない状態を減らすことです。知見を参照できる状態にしておくことで、同じ調査を繰り返さずに済み、移行後半の速度が落ちにくくなりました。

## 5. セキュリティは、設定項目を1つずつ調べながら詰めた

移行にあわせて、セキュリティまわりの対応も担当しました。使ったのは Nuxt Security（nuxt-security）というモジュールで、やること自体は nuxt.config に設定値を書いていくのが中心です。

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-security'],
  security: {
    headers: {
      contentSecurityPolicy: {
        'default-src': ["'self'"],
        'script-src': ["'self'"],
        'img-src': ["'self'", 'data:']
        // ...
      },
      strictTransportSecurity: {
        maxAge: 31536000,
        includeSubdomains: true
      }
      // ...
    }
  }
})
```

ただ、設定項目の意味が分からないまま値を入れても意味がありません。CSP の各ディレクティブや、HSTS、X-Frame-Options といったヘッダー類について、「これは何を防ぐためのものか」「値を強めると何が起きるか」を、ドキュメントやセキュリティ情報を1つずつ調べながら、サービスに合わせて値を決めていきました。

## 6. 結果 — 移行リリース完了と、脆弱性診断 A評価（100点／100点）

移行リリースは完了し、移行後の脆弱性診断では A評価（100点／100点）を取得しました🎉

この数字は移行の目的そのものではありませんが、基盤を刷新しながら品質を落とさなかったことの裏付けにはなると思っています。

## 7. その後 — Nuxt 4 への移行にもつながった

その後、Nuxt 3 から Nuxt 4 へのアップデートも担当し、リリースを完了しました。併せてチームのタスク管理と不具合調査も担当しました。

また、ソースマップ導入後のデバッグ環境を活用するため、VS Code・ブラウザのデバッグツールに関する勉強会を実施し、調査効率が向上したとのフィードバックをもらいました。

Nuxt 3 の移行で作った「ソースまで確認する」「並走のルールを決める」「知見を残す」というやり方は、Nuxt 4 のときにもそのまま使えました。

## まとめ

- ドキュメントにない挙動は、ソースコードまで確認してから判断した
- 「Nuxt instance is unavailable」の調査では、Vue のインスタンス管理と、SSR で Cross-Request State Pollution を防ぐ制約が背景にあることまで整理した
- 機能開発との並走は、移行用リポジトリ・開発環境・取り込みルールで支えた
- 調査結果は GitHub Discussions に残し、追加メンバーのキャッチアップに使った
- セキュリティは Nuxt Security の設定項目を1つずつ調べながら詰めた
- 結果として移行リリースを完了し、脆弱性診断で A評価（100点／100点）を得た

大規模サービスのメジャーアップデートは、技術的な正しさだけでは進みません。並走する開発と、途中で増えるメンバーと、移行後の品質を、同時に回す段取りが必要でした。その段取りを含めて、移行の仕事だったと思っています👋🏻
